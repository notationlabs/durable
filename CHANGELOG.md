# Changelog

## Unreleased

### Breaking changes

- YieldStar is renamed Durable. The packages publish as `@notation/durable` and `@notation/durable-conformance`, and the `yieldstar` and `@yieldstar/*` packages are no longer published. Replace the imports as follows:
  - `yieldstar` → `@notation/durable`
  - `@yieldstar/core` → `@notation/durable/runtime`. `ExecutionDispatcher`, `WorkflowRunner` and the `EventContext` type are also exported from `@notation/durable`.
  - `@yieldstar/http-server` → `@notation/durable/http`
  - `@yieldstar/worker-invoker` → `@notation/durable/worker`
  - `@yieldstar/sqlite-runtime`, `/bun` and `/node` → `@notation/durable/sqlite`, `/sqlite/bun` and `/sqlite/node`
  - `@yieldstar/runtime-conformance` → `@notation/durable-conformance`, which has `@notation/durable` as a peer dependency.
- `createSqliteDb` defaults to `./.db/durable.sqlite` instead of `./.db/yieldstar.sqlite`. An application that relied on the default must pass `path: "./.db/yieldstar.sqlite"` or move the file.
- `HeapClient.writeStep` takes an optional `deleteWaitersOf`, a list of other step keys whose store, effect and join waiters a `done` record deletes in the same write. The driver passes it when it records a `step.all` or `step.race` decision. Runtime adapters must honour it; `registerStoreClientConformance` checks it.
- `step.delay` and `step.poll` are typed `AsyncGenerator<StepResponse, void, any>` instead of `any`. Code that used their result as a value no longer typechecks.
- `EffectClient.settle` takes `status: "settled"` with a `result` or `status: "failed"` with an `error`. A `conflict` result, and each `EffectConflictReport`, carry `outcome` and `conflictingOutcome` instead of `result` and `conflictingResult`. `begin` can return `failed` with the stored error, and `EffectRecord.status` can be `failed`, with the error in `error`. `EffectState` and `EffectConflictState` store each side's status. Runtime adapters must store and return failed effects; `registerEffectClientConformance` checks them.
- `ExecutionClient` has a required `list` method, and `admit` takes `idempotent` and can return `{ status: "existing", executionId }`. `ExecutionAdmissionErrorCode` gains `EXECUTION_REQUEST_MISMATCH` and `IDEMPOTENT_TRIGGER_REQUIRES_ID`. Runtime adapters must assign each admitted execution an admission sequence, answer a used ID with `matchExecutionAdmission`, and implement `list`; `registerExecutionClientConformance` checks them.
- Every error response from `@yieldstar/http-server` has the body `{ code, message }`. `/events` responds `404` with `EXECUTION_NOT_FOUND` instead of the text `Execution not found`, and `400` with `INVALID_OBSERVATION_REQUEST` for a missing `executionId`. A route that throws, such as `/trigger` when admission throws, responds `500` with `INTERNAL_ERROR` and the fixed message `Internal error` instead of the error message as a JSON string; the server logs the error.
- `/poll`, `/wait`, `/list` and `/events` accept every request unless `observationMiddleware` is configured. Trigger `middleware` does not apply to them. A deployment that guards `/trigger` with middleware should add `observationMiddleware` before upgrading; `createRoutes` logs a warning when trigger middleware is set without it.
- `createLocalSdk` throws a `RangeError` for a `pollInterval` that is not a finite number greater than zero.
- Removed `waitForExecutionOutcome` from `@yieldstar/core`. Use `createExecutionObserver(executions, { pollInterval?, notifier? }).wait(executionId)` instead. It takes an object with `get` and `list`, accepts the invoker's `workflowEndEmitter` as `notifier` in place of `emitter`, and resolves with the terminal view, which has the outcome's `status` and `result` or `error` together with `executionId`, `workflowId`, `admittedAt` and `updatedAt`.
- The HTTP SDK's `waitForResult` posts to `/wait` instead of `/events`, so the server must expose the routes from this release. An error response that is not a rejected admission or list request throws `HttpRouteError`, with the response's `status` and `code`, instead of the response's `statusText` string.
- `ExecutionClient` has a required `cancel` method, and `HeapClient` has a required `recordCancellation` method. `cancel` records a request and propagates it to every non-terminal, non-detached descendant all-or-nothing; a forced request also records `cancelled`, clears the pending wake, deletes the waiters the execution holds, wakes its join waiters and issues a higher lease token. `recordCancellation` is a fenced write of the delivered throw's step records, the deletion of those steps' waiters and `deliveredAt`; it writes nothing if a step already has a different record. A forced cancel does not pass through the dispatcher, so `workflowEndEmitter` emits only for an execution whose delivery ended `cancelled`, with a `WorkflowCancelledError`. Runtime adapters build both from the state helpers in `@yieldstar/core`; `registerCancellationClientConformance` checks them.
- `ExecutionStatus` gains `cancelled`, `ExecutionOutcome` and `TerminalExecutionView` gain `{ status: "cancelled", reason?, source? }`, and `WorkflowRunOutcome` gains `{ status: "cancelled" }`. Code that switches over a status or outcome must handle the new variant. `isTerminalExecutionStatus` and `isTerminalExecutionView` return `true` for it.
- `ExecutionParent` has a required `detached` field, and `ExecutionRecord` and execution views gain an optional `cancellation`. `ExecutionStartRequest` takes `detached`, and `StartRequestState` and `PreparedExecutionStart` carry it. A repeated start with a different `detached` returns `START_REQUEST_MISMATCH`.
- `DeliveryOptions` and `WorkflowGeneratorParams` carry the record's `cancellation`, and the worker IPC `deliver` message carries it as `cancellation`. A custom `WorkflowInvoker` must pass it on to `WorkflowRunner.run`, or its deliveries run as if no request were recorded. Every process that shares a backend must be upgraded before anyone calls `cancel`.
- `RetryableError` throws a `RangeError` when `maxAttempts` is not a positive integer or `retryInterval` is not a finite number of at least zero. A `retryInterval` of `0` now retries without waiting; it used to wait 60 seconds. `step.poll` builds a `RetryableError` from its options, so a `step.poll` with such options fails with the `RangeError` when its predicate first returns `false`.

### Added

- `@notation/durable/testing` runs workflows in memory, without a worker process or a database file. `createTestSdk(router, { logger?, clock? })` returns a local SDK over a new `MemoryRuntime`, together with that `runtime` and the `dispatcher` it starts on the first trigger. The entry point also exports `MemoryRuntime` and `createInProcessInvoker`, which delivers executions in the calling process.
- `workflow` and `createWorkflow` default their type parameters to `EventParams`, `DurableValue | void` and `EventContext`, so `workflow<Params, Result>` and `workflow<Params>` typecheck.
- `StoreValidationError` is exported from `@notation/durable`.
- `step.effect` infers its result type from `perform` only. A `lookup` that returns `{ status: "not-found" }` in one branch no longer adds `undefined` to the result type.
- `step.all(key, branches, { concurrency?, mode? })` and `step.race(key, branches)` drive branches of steps concurrently within one delivery. A branch is any step generator, including an `async function*` that runs several steps and a nested `all` or `race`. `all` returns the results in branch order; in `fail-fast` mode (the default) the first branch failure is thrown, and `mode: "settle"` returns `{ status: "fulfilled", value }` or `{ status: "rejected", error }` for each branch. `race` returns `{ index, value }` for the first branch to succeed, and throws `WorkflowRaceError` (`ALL_BRANCHES_FAILED`, with `errors` in branch order) when every branch fails. Each combinator records only its decision under its own key, and every delivery resumes every branch through its recorded steps, so replay returns the same results and the same winner. A delivery with suspended branches ends `suspended` once, with the earliest wake time. Losing and fail-fast branches are abandoned: they start no new steps, their `finally` blocks do not run, and the decision's write deletes their waiters; a step function already running finishes and is recorded before the combinator returns. A store or join wait checks its condition before a race decides, so a satisfied wait that is the last step of its branch wins against a delay that elapsed. Inside a branch, a step in retry backoff, or an effect step waiting for `retryIn`, is not run again before it is due when another branch wakes the execution; a retry record now holds the time the retry is due. Step keys inside branches are not prefixed and must be unique across the execution. Cancellation inside a combinator is thrown into every unfinished branch in one fenced write that also records the combinator as `cancelled`; the combinator throws `WorkflowCancelledError` once every branch has finished.
- The delivery that passes a `step.delay` records it as passed, as the step's next attempt, before the workflow continues. Replay passes it without reading the clock, so a clock that reads earlier on a later delivery no longer suspends the workflow at a delay it already passed. An execution already in progress writes this record once for each delay in its history that it passes on replay, on its first delivery after the upgrade.
- `yieldstar` and `@yieldstar/core` export `WorkflowRaceError`, registered by default; `yieldstar` exports the types `Branch`, `BranchResults`, `SettledResult`, `SettledResults`, `RaceResult` and `AllOptions`.
- `WorkflowStore.when(key, selector, { deadline })` waits for the selector to match or for an absolute `deadline`, whichever is recorded first, and returns `TimedWhenResult<R>`: `{ status: "matched", value }` or `{ status: "timed-out" }`. The first evaluation records the deadline with the unfinished step, and later evaluations use the recorded deadline. Each evaluation runs the selector first, so a match returns `matched` even after the deadline. An unresolved wait records the deadline with the unfinished step, then registers its waiter, then suspends with `wakeAt` set to the deadline. A `when` or `take` without a deadline now takes the same steps, so it records its unfinished step before it registers its waiter, and each delivery writes that record once; the write that records the result deletes the waiter. The timed form requires an explicit key and a `deadline`. The form without a deadline is unchanged.
- `StepStoreWait` takes an optional `wakeAt`, which `WorkflowRunner` reports as the suspended outcome's `wakeAt`.
- `registerExecutionClientConformance` checks a store waiter combined with a suspended `wakeAt`.
- The local and HTTP SDKs have `poll(executionId)`, `wait(executionId, { timeout?, signal? })` and `list({ workflowId?, status?, cursor?, limit? })`, and implement `ExecutionObserver`. They read the execution record, so they return outcomes recorded by any process that shares the backend, before or after the call, and across a restart. `wait` reads the record before it waits, resolves with `{ status: "timed-out", execution }` when its timeout passes, resolves with `undefined` at once for an unknown ID, and stops reading and rejects with the signal's reason when `signal` aborts. `list` returns views newest first by admission sequence, 50 per page by default and at most 1000, with an opaque cursor, and an invalid request throws `ExecutionListRequestError` (`INVALID_LIST_REQUEST`). A view leaves out `params`, `context`, lease and wake state and `unacknowledgedDeliveryCount`. The HTTP SDK's `poll` and `wait` resolve with `undefined` only for a `404` with code `EXECUTION_NOT_FOUND`; any other `404`, such as one from a wrong base path, throws `HttpRouteError`.
- `trigger` takes `idempotent: true` with an `executionId`. A repeat with the same `workflowId` and canonical `params` resolves with `status: "existing"` and admits nothing, whatever the existing execution's status; a different request throws `ExecutionAdmissionError` (`EXECUTION_REQUEST_MISMATCH`), and a missing ID throws `IDEMPOTENT_TRIGGER_REQUIRES_ID`. `TriggerEvent` is typed so that `idempotent: true` without `executionId` is a type error. `context` is not compared. `trigger` resolves with a `TriggerAck`, `{ executionId, status }`.
- `triggerAndWait` and the HTTP SDK's `waitForResult` are `trigger` followed by `wait` without a timeout, and no longer depend on `workflowEndEmitter`.
- `createRoutes` registers `POST /poll`, `POST /wait` and `POST /list`, and takes `observationMiddleware`, an array of `ObservationMiddlewareFunction`s that allow or deny observation requests before any record is read. A denial responds `401` `UNAUTHORIZED` or `403` `FORBIDDEN`, never `404`. `/wait` holds a request open for at most `maxWait`, a `createRoutes` option that defaults to 8000 ms and must be a finite number greater than zero, and then responds `timed-out`; the HTTP SDK repeats it. `/wait` and `/events` stop reading the record when the client disconnects. `/trigger` takes `idempotent`, responds `200` with `status: "existing"` for a matching repeat, `409` for `EXECUTION_REQUEST_MISMATCH` and `400` for `IDEMPOTENT_TRIGGER_REQUIRES_ID`, and adds `status: "accepted"` to its `202` body. Trigger middleware does not run for the observation routes. `createRoutes` takes `pollInterval`, how often each open `/wait` and `/events` request reads the record (default 25 ms, and a finite number greater than zero); each open request reads on its own.
- `POST /events` is deprecated: use `/wait`. It keeps its response shape and runs observation middleware.
- `@yieldstar/core` exports `createExecutionObserver`, `toExecutionView`, `isTerminalExecutionView`, `isDuration`, `isPositiveInterval`, `ExecutionListRequestError`, the view types, and the list helpers for adapter authors (`prepareExecutionListRequest`, `matchesExecutionListRequest`, `toExecutionListPage`). `yieldstar` re-exports `ExecutionListRequestError`, `HttpRouteError`, `TriggerAck`, `ExecutionObserver` and the view types.
- `SqliteExecutionClient.list` orders executions by the `executions` table's `rowid`, which SQLite assigns under the write lock in insert order, so existing databases need no migration. `SqliteRuntime` creates indexes on `executions(workflow_id)` and `executions(status)`. No index serves `status: "running"`, which is derived from `lease_expires_at`, so that filter reads rows newest first until it fills a page. A `VACUUM` may renumber the `rowid`s and invalidate a list cursor held across it.
- `registerExecutionClientConformance` checks idempotent admission and `list`, including order across two clients with skewed clocks.
- The local and HTTP SDKs have `cancel(executionId, { reason?, force? })`, and implement `ExecutionControl`. `cancel` records a request and returns without waiting for the workflow to stop. It resolves with `{ status: "requested", execution }` for an active execution, with the terminal view when the execution is terminal (including after a forced cancel), and with `undefined` for an unknown ID. An empty ID, or a `reason` or `force` of the wrong type, throws `ExecutionCancelRequestError` before anything is recorded or sent.
- A graceful cancel makes the execution due. Its next delivery replays the finished steps and throws `WorkflowCancelledError` (`reason`, `source`) into workflow code at the first unfinished step, instead of running or suspending it. The throw is recorded as the step's result, as a `step-cancelled` record, in one fenced write that also deletes the step's waiters and sets `cancellation.deliveredAt`, so replay throws the same error at the same step. A running step function is not interrupted, and a delivery already in progress carries on without the request. Cleanup steps after the throw run, suspend and wake as usual. A workflow that lets the error escape ends `cancelled`; one that catches it and returns ends `completed`. `WorkflowCancelledError` is registered by default.
- `force: true` records `cancelled` at once without running workflow code, and fences out any worker that holds the execution's lease.
- A cancellation request propagates to every non-terminal child that `step.start` or `step.call` started, recursively, with the same `force`, the parent's first `reason`, and the execution where the cancellation began as `source`. `step.start` and `step.call` take `{ detached: true }`, which records the child's parent link as detached so it receives no propagated request.
- `step.join` and `step.call` on a cancelled target throw `WorkflowJoinError` with code `JOINED_EXECUTION_CANCELLED`, carrying the target's `reason` and `source`.
- `triggerAndWait` and the HTTP SDK's `waitForResult` throw `WorkflowCancelledError` for a cancelled execution. `wait` returns the cancelled view, and `list` accepts `status: "cancelled"`.
- `createRoutes` registers `POST /cancel`, which takes `{ executionId, reason?, force? }` and responds `202` with `requested`, `200` with a terminal view, `404` `EXECUTION_NOT_FOUND` or `400` `INVALID_CANCEL_REQUEST`. Observation middleware runs for it with `operation: "cancel"`, the `executionId`, `force` and `load()`, so a policy that allows reads must check `operation` to deny cancels. The warning that `createRoutes` logs for trigger `middleware` without `observationMiddleware` also names `/cancel`. `/events` responds `500` with an encoded `WorkflowCancelledError` for a cancelled execution. A `403` from observation middleware now has the message `Request denied` instead of `Observation denied` on every observation route.
- `@yieldstar/core` exports `createExecutionControl`, `ExecutionCancelRequestError`, `WorkflowCancelledError`, and the cancellation helpers for adapter authors (`prepareExecutionCancel`, `requestExecutionCancellation`, `propagatedCancellation`, `cancellationForStartedChild`, `markCancellationDelivered`, `toExecutionCancellation`). `yieldstar` re-exports `WorkflowCancelledError`, `ExecutionCancelRequestError`, `ExecutionControl`, `CancelOptions`, `CancelResult`, `ExecutionCancellation` and `StartOptions`.
- `SqliteExecutionClient` adds `parent_detached` and the `cancellation_*` columns, and an index on `parent_execution_id`, to an existing `executions` table, and `detached` to an existing `start_requests` table. Existing rows read as attached children with no request.
- `registerCancellationClientConformance` checks `ExecutionClient.cancel`, its propagation, and `HeapClient.recordCancellation`.
- `step.effect` takes an optional `failsOn(error)`. When `perform` throws and `failsOn` returns `true`, the effect fails with the error, the step records and throws it, and every execution that begins the same effect ID receives it. `lookup` can return `{ status: "failed", error }`. A second failure keeps the first error without a conflict report.
- `step.effect` takes an optional `maxAttempts`. When an attempt ends uncertain and it is attempt number `maxAttempts`, the step throws `WorkflowEffectError` with code `EFFECT_OUTCOME_UNKNOWN` instead of suspending, and the effect stays pending.
- `SqliteEffectClient` adds `status` and `conflicting_status` columns to an existing `effect_conflicts` table, and reads existing conflict reports as conflicts between two results.

- `durableValueCodec` encodes `Date`, `Map`, `Set` and `bigint` as tagged values and decodes them back to the same type, so step results, store state, params, context, effect inputs and results, and workflow results may hold them. Map entries and set values keep their insertion order. Invalid `Date`s, subclasses of these types and instances with own properties are still rejected. `Durable<T>` accepts these types, and still rejects functions.
- Store updaters can mutate `Date`s, `Map`s and `Set`s in a draft. A write through one of their methods wakes waiters on the value's path.

### Fixed

- A `when` selector that throws records the error as the step's outcome, as `select` and `take` already did. The error used to escape the step unrecorded, so a workflow that caught it failed with `Workflow yielded an invalid step` or `Cannot record a step-key step response`.

## 0.6.1 - 2026-10-29

### Added

- `ExecutionClient.claimDue` takes an optional `filter: { executionIds }` and claims only executions whose ID is in it, atomically with the claim. An empty list claims nothing. The SQLite and memory runtimes implement it, and `registerExecutionClientConformance` checks that a filtered claim leaves other executions unclaimed.
- `ExecutionDispatcher` takes a `filter` option and passes it to every claim, so a process can run only the executions it was asked to run without claiming, failing or delaying other executions in a shared backend. An empty `filter.executionIds` throws a `RangeError`.

## 0.6.0 - 2026-10-29

### Breaking changes

- Executions now have a durable execution record. Removed `SqliteEventLoop`, `SqliteTaskQueue`, `SqliteTaskQueueClient`, `SqliteTimersClient`, `SqliteSchedulerClient`, `MemoryEventLoop`, `MemoryTaskQueue`, `MemoryTimers`, `MemorySchedulerClient`, and the core `SchedulerClient` and `EventProcessor` types. Construct a `SqliteRuntime` or `MemoryRuntime` and run an `ExecutionDispatcher` instead.
- `WorkflowRunner` takes a runtime: `new WorkflowRunner(runtime, { router, logger })`. `run()` resolves with a `WorkflowRunOutcome` (`completed`, `suspended` or `failed`) and rejects only on infrastructure errors. An unregistered `workflowId` resolves as `failed` instead of throwing.
- `WorkflowInvoker.execute(event)` is replaced by `deliver(event)`, which resolves with the delivery's outcome. `workflowEndEmitter` is deprecated. The worker IPC protocol now reports `outcome` and `error` messages.
- `createLocalSdk(invoker)` is now `createLocalSdk(runtime, { invoker?, pollInterval? })`. `trigger` resolves once admission commits and no longer runs anything; a dispatcher must be running. `triggerAndWait` reads the execution record and rejects with the recorded error.
- `createRoutes({ invoker, ... })` is now `createRoutes({ runtime, invoker?, ... })`. `POST /trigger` admits the execution and returns `409` when the execution ID is in use and `400` when the event cannot be stored without loss. `POST /events` returns `404` for an unknown execution.
- Execution IDs are unique and never reused. Triggering with an ID already admitted throws `ExecutionAdmissionError` (`EXECUTION_ID_CONFLICT`). The HTTP SDK no longer generates IDs client-side; it reads the accepted ID from the trigger response.
- Admission rejects `params` and `context` that do not round-trip through JSON exactly, such as `Date`s, class instances, `undefined` properties, `NaN`, and `bigint` (`INVALID_EXECUTION_EVENT`).
- Execution `params`, `context` and outcomes are stored with `durableValueCodec`, and values written in the earlier format are not read. Admission accepts `undefined` and errors anywhere in `params` and `context`, and rejects `context` keys that are not strings (`INVALID_EXECUTION_EVENT`). A failed outcome's error keeps its registered class, `code`, `cause` and durable fields. A completed result the codec rejects is recorded as `failed` with `WorkflowValueError` (`INVALID_STEP_VALUE`).
- Step records are encoded with `durableValueCodec` instead of `serialize-error`, and records written in the earlier format are not read; let in-flight executions finish before upgrading. A `step.run` result, a store step's result, store state or a workflow result that is not a durable value, such as a `Date`, `Map`, `Set`, `bigint` or class instance, now throws `WorkflowValueError` (`INVALID_STEP_VALUE`) on the first run instead of changing on replay. An invalid workflow result fails the execution with the step key `$$workflow-result$$`.
- Workflow code receives the decoded copy of every step result on the first run as well as on replay, so it never sees the object the step function returned. Error-shaped plain objects stay plain objects, `undefined` properties keep their keys, and plain objects with a `$type` key read back unchanged.
- A recorded step error keeps its registered class, `code`, `cause`, `stack` and durable fields; other properties are omitted on the first run too. A thrown value that is not an error is rethrown as thrown, or as `Error(String(value))` when it is not durable.
- `step.run`'s function result is typed with `Durable<T>`, so returning a `Date`, `Map`, `Set`, `bigint` or function is a type error.
- Store state that is not a durable value after schema validation is rejected with `WorkflowValueError` (`INVALID_STEP_VALUE`) and leaves the store unchanged, as does a `take` selection. Store connectors encode state and step receipts with `durableValueCodec` (`encodeStoreValue`, `decodeStoreValue`).
- The worker IPC protocol sends event params and context as `encodeExecutionEvent` encodings, and results and errors as `durableValueCodec` encodings.
- `POST /trigger` reads its body, and `POST /events` writes the result or error, with `durableValueCodec`. Plain JSON remains a valid trigger body. The HTTP SDK's `waitForResult` throws the recorded error as its registered class rather than a plain `Error`, and `trigger` rejects non-durable params or context with `INVALID_EXECUTION_EVENT` before sending a request.
- `yieldstar`, `@yieldstar/worker-invoker` and `@yieldstar/http-server` no longer depend on `serialize-error`.
- `DurableValue` gains `undefined` and `Error`, so `ExecutionClient.start` accepts params with `undefined` properties; `{ a: undefined }` and `{}` do not match.
- Infrastructure errors, such as the SQLite database throwing during a store step, no longer reach workflow `try/catch`. The delivery is not acknowledged and is redelivered after the redelivery delay. Store validation and not-found errors, and errors thrown by updaters, selectors and claims, remain catchable.
- Removed `StoreWaiter.event` and the SQLite `store_wake_outbox` table. `SqliteStoreClient` takes `{ db, executions? }` instead of a scheduler client.
- `registerStoreClientConformance` factories return `{ runtime, createPeer?, restart?, dispose? }` instead of building a store client from a scheduler.
- `MiddlewareEvent.executionId` is optional; it is absent when the runtime will choose the ID.
- Executions are delivered under leases with fencing tokens, replacing the fixed redelivery timeout. `ExecutionDelivery` is replaced by `ExecutionLease` (`{ executionId, token, expiresAt }`). `claimDue` takes `{ limit, duration }` and returns leases earliest due first; `acknowledge` takes `{ lease, outcome }` and returns `{ status: "lost" }` for a stale lease. `ExecutionStatus` gains `running`, and `ExecutionRecord` gains `unacknowledgedDeliveryCount`.
- `HeapClient.writeStep` takes `{ lease, stepKey, stepAttempt, done, stepResponseJson }` instead of an `executionId` and `stepDone`, and resolves with the record as stored or `{ status: "lost" }`. Rewriting an existing record no longer throws; it returns the existing record unchanged.
- `WorkflowInvoker.deliver(event, { lease, signal })` and `WorkflowRunner.run(event, { lease, signal, logger? })` take a `DeliveryOptions` object with the delivery's lease and an `AbortSignal`. `WorkflowGeneratorParams` carries the `lease` and `signal`. The worker IPC protocol sends `{ type: "deliver", event, lease }` to start a delivery; there is no abort message, because the worker invoker kills a worker whose lease is lost.
- A delivery that ends without an outcome is redelivered after a redelivery delay that starts at 1 second and doubles with each consecutive unacknowledged delivery, up to 5 minutes, instead of after five minutes.
- `StepDelay.resumeIn` and `WorkflowDelay.resumeIn` are renamed `wakeAt`. Delay and retry steps read their wake time from the runtime clock instead of `Date.now()`, and `WorkflowGeneratorParams` carries that `clock`.
- `WorkflowGeneratorParams` carries an `executionClient`, which `WorkflowRunner` sets from its runtime's `executions`.
- `WorkflowGeneratorParams` carries an `effectClient`, which `WorkflowRunner` sets from its runtime's `effects`. Code that builds `WorkflowGeneratorParams` by hand must pass one.
- `@yieldstar/store-conformance` is renamed to `@yieldstar/runtime-conformance`, since its suites qualify a whole runtime. The exports are unchanged.
- `defineStore(name, schema, { initial })` requires `initial(id)`, a synchronous function returning the state of a new store, and `StoreDefinition` carries it. Every store operation, in workflows and through `StoreClient`, creates a missing store from `initial(id)` in the same atomic write as the operation; `initial` runs only when the store is missing, and concurrent operations on a missing store record one initial state. A store deleted between operations is created again by the next one.
- `step.store(definition, { id? })` returns a `WorkflowStore` synchronously, without `yield*`, and records no step. Its `initial` param is removed, and a loop or helper can request the same handle any number of times. A non-durable or invalid initial state is reported by the first operation's step, and an error thrown by `initial` reaches workflow code from that operation.
- `StoreClient.getOrCreateStore` is removed. `StoreDeleteFromResult` loses its not-found variant.
- Store connectors implement `readStore`, `insertStore`, `commitStoreMutation` and `commitStoreDeletion`, and `CasStoreClient` provides `getStore` and `deleteStoreFrom`. A commit computed from a created snapshot inserts the store, or conflicts if another writer created it first.

### Added

- Added `Runtime`, `ExecutionClient` (`admit`, `get`, `requestWake`, `claimDue`, `acknowledge`), `ExecutionRecord`, `ExecutionStatus`, `ExecutionOutcome`, `WorkflowRunOutcome`, `ExecutionAdmissionError`, and `InfrastructureError` to `@yieldstar/core`.
- Added `SqliteRuntime(db, { clock? })` and `MemoryRuntime({ clock? })`, each exposing `clock`, `executions`, `heap`, and `stores`.
- Added `ExecutionDispatcher(runtime, { invoker, logger, pollInterval?, keepAlive? })` with `start`, `stop`, `tick`, and `drain`. It is the only component that delivers executions, and it returns a finished execution's recorded outcome without running workflow code.
- Added `registerExecutionClientConformance` to `@yieldstar/runtime-conformance`, which checks admission, wake merging, claims, acknowledgement and terminal outcomes of any runtime's `ExecutionClient`.
- Added `waitForExecutionOutcome` and the storage-neutral execution state machine (`prepareExecutionAdmission`, `claimExecution`, `acknowledgeExecution`, and related helpers) for runtime adapter authors.
- Added `StoreValidationError`.

### Changed

- A store commit makes each waiting execution due in the same transaction, so a durable commit always has durable wakes.
- Store waiters persist until the step that registered them records its result, instead of being consumed by a wake.
- Any number of wakes for one execution, from delays, retries and store commits, collapse into one delivery at the earliest due time.
- `triggerAndWait` and `POST /events` settle from the execution record, so they settle even if the process that ran the execution restarted.
- Several dispatchers, in one process or in several processes sharing one SQLite file, can deliver executions at once. An execution has at most one live lease, and every heap step write, renewal, release and acknowledgement checks the lease's token atomically, so a stale holder's writes return `lost` and change nothing.
- The dispatcher renews each lease while its delivery runs, so a slow delivery is no longer delivered a second time. A delivery that rejects releases its lease, except when the worker exits before replying, which leaves the lease to expire.
- The driver ends a delivery as a retry when a step is already recorded with a different value; the next delivery replays the recorded value.
- When a renewal returns `lost`, the dispatcher aborts the delivery's signal. The driver checks the signal before each step function and each fenced write, and ends an aborted delivery with an `InfrastructureError` caused by `LeaseLostError`, without running more workflow code. The delivery is neither acknowledged nor released.
- The worker invoker kills the worker (`SIGKILL`) when a delivery's signal aborts, so a step function that hangs stops at once, and `deliver` rejects with the lease-lost `InfrastructureError` rather than `WorkerExitedError`.
- The dispatcher abandons an aborted delivery that has not settled within `abortGracePeriod` (default 1 second) and frees its slot, so an in-process step function that hangs no longer holds a slot forever. The abandoned delivery's late outcome or rejection is ignored.
- When reading the record, acknowledging or releasing throws, the dispatcher leaves the lease to expire rather than releasing it.
- A forked worker exits as soon as its IPC channel to the runtime process closes, so it makes no further writes after that process dies.

## 0.5.0 - 2026-07-21

### Breaking changes

- Renamed `@yieldstar/bun-sqlite-runtime` to `@yieldstar/sqlite-runtime`, `@yieldstar/bun-worker-invoker` to `@yieldstar/worker-invoker`, and `@yieldstar/bun-http-server` to `@yieldstar/http-server`. The old package names are not shipped as compatibility packages; follow the [migration guide](docs/migrations/0.4-to-0.5.md) before upgrading.
- Removed the worker invoker's `executable` option. Parent and worker processes must use the same runtime family because Bun and Node cannot communicate through Node's V8 advanced IPC serialization.
- Store updater callbacks must be synchronous, deterministic, and side-effect-free. `update`, `updateFrom`, and take claims reject promise-returning callbacks because compare-and-swap retries may execute a callback more than once.

### Added

- Added durable workflow stores through `defineStore` and `step.store()`, with `get`, `select`, `update`, `updateFrom`, `deleteFrom`, `when`, and `take` operations.
- Added Standard Schema validation for store state, versioned snapshots and receipts carrying `instanceId` and `version`, and discriminated update and delete results.
- Added compare-and-swap store mutations and an applied-steps ledger so retried workflow store operations have exactly-once semantics, including explicit `already-applied` and `conflict` outcomes.
- Added a minimal synchronous `SqliteDriver` contract and connector entry points at `@yieldstar/sqlite-runtime/bun` and `@yieldstar/sqlite-runtime/node` for real `bun:sqlite` and `node:sqlite` databases.
- Added Node.js support for the resident-process runtime. TypeScript worker entry points require Node 22.6 or newer for built-in type stripping; older Node versions can use compiled JavaScript workers.
- Added one Vitest suite that runs the complete conformance and fork-integration coverage under both Bun and Node.
- Added two-leg GitHub Actions CI pinned to Bun 1.3.14, Node 22.18.0, and pnpm 11.6.0.
- Added a worker `ready` handshake and configurable timeout so missing listeners and unsupported cross-runtime forks fail explicitly instead of hanging.

### Changed

- Made the SQLite heap, scheduler, timers, task queue, event loop, stores, and DAOs independent of a concrete SQLite implementation.
- Replaced `Bun.spawn` worker IPC with `node:child_process.fork`, including propagation of spawn errors and premature child exits. The optional `execPath` can select another binary from the same runtime family.
- Retyped HTTP route handlers with standard `Request` and `Response` APIs while keeping the routes object compatible with `Bun.serve` and other Request-to-Response routers.
- Replaced Bun-specific runtime utilities and targeted all package bundles at Node.
- Replaced `Bun.randomUUIDv7()` with UUID v7 from the `uuid` package.
